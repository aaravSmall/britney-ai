britney.ai — future ideas / plans
(running notes, not commitments — add/cross off freely)

DATA & BACKEND
- Real performance history: dashboard's 30-day chart is still a random mock
  seeded from user id, unrelated to actual trades/holdings. Need a daily
  snapshot table (portfolio value per user per day) to make it real.
- Websocket/streaming quotes instead of polling Yahoo/CoinGecko on each
  dashboard load — cheaper and feels more "live".
- Move off the Yahoo Finance unofficial endpoint before any real launch —
  see docs/TECH_STACK.md for paid alternatives (Alpaca/Polygon/IEX).
- Trade history / order log screen (right now a fill just mutates
  cash + holdings, nothing records that the trade happened).
- Real cash ledger instead of a single cash_balance float (deposits,
  withdrawals, dividends, fees down the line).

TRADING
- REMINDER before the agent (prompt 4) starts trading on a schedule:
  get_or_create_portfolio() is currently only called from build_dashboard's
  path (via ensure_demo_holdings) and from record_trade_fill itself, but
  ensure_demo_holdings is NOT called from record_trade_fill — so a
  portfolio that's never been loaded via /dashboard (pre-existing
  CORS/first-load timing edge case) can still be traded against, just
  without demo seed holdings. Before the agent trades on a schedule
  without a user ever having opened /dashboard first, make
  record_trade_fill call get_or_create_portfolio() directly (it already
  does) AND decide whether it should also seed/initialize like
  ensure_demo_holdings does, so a never-loaded portfolio can't cause a
  failed/mysterious agent trade. Flagged 2026-08-04, not yet implemented.
- Actual Alpaca live/paper order routing (execution.py has a placeholder
  for this — currently everything is simulated locally).
- Fractional share support / rounding rules for crypto vs stock vs option
  quantities.
- Recurring/auto-invest execution (auto_invest_enabled toggle exists but
  nothing runs on a schedule yet).

FRONTEND / UX

- Mobile builds (android/ios folders aren't generated yet — currently

AGENT — CRYPTO NEWS
- INGESTION DONE (2026-08-07): backend/agent/news_ingestion.py now has
  fetch_crypto_news() (CryptoPanic free tier), symmetric to the existing
  fetch_news() (Finnhub) — same NewsArticle shape, same SeenArticleStore
  dedupe discipline, same RateLimiter, same real-vs-mock loud logging.
  target_crypto_tickers()/target_crypto_tickers_for(tier) mirror the
  stock equivalents. Verified: mock-mode fallback (no CRYPTOPANIC_API_KEY)
  produces correctly-labeled placeholder articles for BTC/ETH/SOL, and
  its output flows through agent/sentiment.py's score_batch() completely
  unmodified. Real-API verification against CryptoPanic itself (a live
  key, actual BTC/ETH articles) was NOT done — no key was available at
  implementation time; do that before relying on this in production.
- STILL NOT WIRED IN: agent/decision_loop.py's run_once() only calls
  news_ingestion.target_stock_tickers_for(tier) + fetch_news() — it never
  calls target_crypto_tickers_for()/fetch_crypto_news(), so crypto
  tickers still get zero trading decisions today (not "some fallback
  signal" — they're just absent from the loop's ticker list entirely).
  Wiring this in needs decision_loop.py changes beyond ingestion:
  - run_once() needs to also fetch+merge crypto articles for the tier.
  - _execute() hardcodes asset_type="stock" for both pricing
    (market_data.get_price_for_holding) and execute_trade() — needs an
    asset_type param threaded through instead, sourced from
    TARGET_PORTFOLIOS rather than assumed.
  - Crypto trades 24/7 with no market-hours gating like stocks implicitly
    get (see run_agent.py's scheduler) — the same poll cadence shouldn't
    just be reused verbatim; crypto news can matter as much at 3am as 3pm.
  Deliberately left undone for now — see the commit that added
  fetch_crypto_news() for why (kept ingestion and decision-loop wiring as
  separate changes rather than touching decision_loop.py's live trading
  logic in the same pass).

INFRA
- PROMOTION CANDIDATE (flagged 2026-08-05): the trading agent's droplet
  (see docs/DEPLOYMENT.md) runs Postgres directly on the same box rather
  than a DigitalOcean Managed Database, to keep it free while only the
  three agent-managed model portfolios (conservative/moderate/aggressive)
  exist and there's no real user data at stake. Once real users/production
  data are involved, move to a managed Postgres add-on (~$15/mo at time of
  writing) for automated backups, point-in-time recovery, easier
  scaling, and decoupling the database's lifecycle/uptime from the agent
  process's (right now a bad `systemctl restart britney-agent` or a
  droplet rebuild takes Postgres down with it).
- Deploy backend + Postgres somewhere real (see docs/TECH_STACK.md) — the
  agent now has this (docs/DEPLOYMENT.md), the FastAPI web app still doesn't.
- CI: no tests or lint pipeline exist yet.
- Alembic migrations instead of relying on create_all (breaks on schema
  changes to existing DBs — currently working around this by deleting
  the local sqlite file).

On the two disclosed tradeoffs:

1. Options no longer suggestable for high-risk users — CC's right 
that this path was never grounded before anyway, so you're not losing 
real functionality, just an ungrounded placeholder. I'd call this a 
non-issue for now — worth a one-line note in IDEAS.txt if you want 
options support later, but not worth solving today.

2. Event-loop blocking, now several calls deep — this one I'd take 
more seriously, but not urgently. It's fine with zero concurrent 
users (now), but it's the kind of thing that turns into a real bug 
the moment two people hit /recommendations at once — one user's 
request blocks everyone else's for ~10s. The likely fix is small 
(FastAPI runs sync def route handlers in a threadpool automatically, 
or wrap the blocking calls in run_in_threadpool) but it's app-wide, 
not specific to this endpoint, so it's a reasonable thing to batch 
with your Sprint 8-9 bug pass rather than solve mid-sprint-6.
